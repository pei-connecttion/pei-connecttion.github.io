      # Goal
      **Develop a system to manage and optimize associations’ workflows**
      ## State of the Art Analysis
      ![State of the Art Comparison](/images/milestones/m1/sota.png)
      ![State of the Art Comparison](/images/milestones/m2/sota2.png)

      ## Actors
      **Board, Sections and Members**
      - We will focus on the most interesting aspect of the system, the one that truly differentiates us from our competitors.
      - The system involves three main actors: the Board, the Sections, and the Members.
      - Over the past few weeks, we have identified at least 35 use cases involving these actors.

      ## Use Case Diagram
      ![Use Case Diagram](/images/milestones/m2/usecase.png)

      ## Requirements
      **Functional Requirements**
      - The system must allow board to view reports and stats about the total number of members, roles and quota payment status
      - The system must require all expenses to be justified, specifying where the funds were spent and including a receipt
      - The system must allow the board to create new roles
      - The system must allow access to the association’s details and expenses
      - The system must allow authorized users roles to register new products 
      - The system must allow users to search for products by name
      - The system must record movement details in the inventory
      - The system must list all available plugins

      **Non-Functional Requirements**
      - The system should support at least 100 concurrent users without performance degradation 
      - The system should degrade gracefully so that platform is not affected by failures.
      - The system should use RBAC (Role-based access control) to manage user roles and enforce permissions.
      - The system should have 90% uptime, resulting in a maximum of 36.5 days of downtime per year.
      - Protection from SQL injection, Cross-Site Scripting, and Cross-Site Request Forgery attacks should be enforced across all API endpoints.
